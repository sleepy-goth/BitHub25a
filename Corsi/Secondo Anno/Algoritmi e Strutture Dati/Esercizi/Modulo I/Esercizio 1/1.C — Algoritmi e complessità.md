### Ordinamento lineare — range polinomiale
Ripasso: [[04 - Algoritmi di Ordinamento]].
> [!question] Traccia tipica — 18/07/2022, 16/07/2024, 12/09/2023, 30/01/2024, 21/01/2025, 18/07/2025, 23/09/2025, 19/02/2024
> Dato un array di $n$ interi con valori in $[1, n^k]$ (con $k$ costante positivo), proporre l'algoritmo di ordinamento più efficiente e calcolarne la complessità.

**Svolgimento.** Integer Sort diretto richiederebbe un array di contatori di taglia $n^k$, con costo $O(n + n^k)$ — inaccettabile per $k \ge 2$. La soluzione ottima è **Radix Sort in base $n$**: ogni chiave in $[1, n^k]$ si rappresenta con $k$ "cifre" in base $n$, ciascuna nell'intervallo $[0, n-1]$. Si eseguono $k$ passate di Integer Sort, ciascuna con dominio di taglia $n$ e costo $O(n + n) = O(n)$, per un totale di $O(kn) = O(n)$ poiché $k$ è costante.

Esempi:
- Range $[1, n^4]$: $k=4$ cifre in base $n$ → $O(n)$ (es. 18/07/2022, 30/01/2024).
- Range $[1, n^2]$: $k=2$ cifre → $O(n)$ (es. 16/07/2024, 21/01/2025, 18/07/2025).
- Range $[n, n^2]$: ampiezza $n^2 - n + 1 \approx n^2$, ancora $k=2$ cifre in base $n$ → $O(n)$ (es. 12/09/2023, 23/09/2025).
- Range $[1, n\log\log n]$: pur non essendo della forma $n^k$, vale $n\log\log n = O(n^2)$ (poiché $\log\log n \le n$), quindi $k = O(n^c)$: bastano $\lceil\log_n(n\log\log n)\rceil = 2$ passate → $O(n)$ (es. 19/02/2024). Integer Sort *diretto* costerebbe invece $O(n + n\log\log n) = O(n\log\log n)$, superlineare.

**Risultato:** Radix Sort in base $n$, $k$ passate di Integer Sort.
**Complessità:** $O(n)$.
**Trappola:** Integer Sort diretto richiede $\Theta(k)$ tempo/spazio (es. $\Theta(n^k)$, oppure $\Theta(n\log\log n)$): non lineare. La condizione di linearità del Radix è $k = O(n^c)$ con $c$ costante — quindi anche un range non-potenza come $n\log\log n$, che è $O(n^2)$, va in $O(n)$; la scelta della base $n$ (non $10$, non $2$) è il punto chiave.
### Ordinamento lineare — range costante
Ripasso: [[04 - Algoritmi di Ordinamento]].
> [!question] Traccia tipica — 22/06/2022, 14/09/2022, 28/09/2022, 18/02/2025, 20/02/2023
> Ordinare $n$ interi con valori in un intervallo di cardinalità costante $C$ (es. $[1, 200]$, voti da $18$ a $30L$, oppure $[n^3, n^3+100]$).

**Svolgimento.** Se la cardinalità dell'intervallo $C$ è costante, **Integer Sort** alloca un array di $C$ contatori. L'*offset* è il valore minimo dell'intervallo, da sottrarre a ogni chiave per ottenere un indice in $[0, C-1]$. Costo: $O(n + C) = O(n)$ poiché $C = O(1)$.

Esempi:
- $[1, 200]$: $C = 200$ contatori, offset $= 1$ → $O(n)$ (es. 22/06/2022).
- Voti $18$–$30L$ ($13$ valori distinti): $C = 13$ → $\Theta(n)$ (es. 14/09/2022).
- $[n^3, n^3+100]$: offset $= n^3$, $C = 101$ contatori → $O(n)$ (es. 28/09/2022, 18/02/2025).
- Vettore di $n$ bit $V[i] \in \{0,1\}$: caso degenere $C = 2$, offset $= 0$ → si contano $0$ e $1$ (due contatori scalari) e si riscrive $V$ → $O(n+C) = O(n)$ poiché $C = 2 = O(1)$, con $O(1)$ spazio ausiliario (es. 20/02/2023).

**Risultato:** Integer Sort con offset.
**Complessità:** $O(n)$.
**Trappola:** allocare un array di taglia pari al valore massimo ($n^3 + 100$) invece di taglia $C = 101$; omettere l'offset genera indici scorretti.
### Ricerca binaria su vettore ordinato
Ripasso: [[05 - Strutture Dati Elementari e Dizionari]].
> [!question] Traccia tipica — 04/07/2023, 22/06/2022, 26/06/2025
> Dato un array ordinato di $n$ elementi con accesso diretto, cercare un elemento $x$. Contare le occorrenze del valore minimo.

**Svolgimento.** L'**accesso diretto** (indice $i$ → $A[i]$ in $O(1)$) permette di raggiungere l'elemento centrale in tempo costante. La ricerca binaria dimezza iterativamente lo spazio di ricerca:
- Mantiene gli indici $[l, r]$; calcola $\text{mid} = \lfloor (l+r)/2 \rfloor$.
- Confronto con $A[\text{mid}]$: se $= x$ → trovato; se $< x$ → $l = \text{mid}+1$; se $> x$ → $r = \text{mid}-1$.
- Terminazione in $O(\log n)$ iterazioni.

Per contare le occorrenze del minimo (pari a $A[1]$ in array ordinato crescente): trovare con ricerca binaria l'ultimo indice $j$ tale che $A[j] = A[1]$; il conteggio è $j$ (es. 04/07/2023).

**Risultato:** ricerca binaria sull'array con accesso diretto.
**Complessità:** $O(\log n)$.
**Trappola:** su lista puntata la ricerca binaria costa $O(n)$ perché il nodo centrale non è raggiungibile in $O(1)$.
### Ricerca in lista concatenata ordinata
Ripasso: [[05 - Strutture Dati Elementari e Dizionari]].
> [!question] Traccia tipica — 28/09/2022, 09/09/2024, 21/01/2025, 16/02/2026, 18/02/2025
> Si ha una lista concatenata con $n$ record ordinati per chiave. Trovare un elemento con chiave $x$.

**Svolgimento.** In una lista concatenata l'accesso agli elementi è esclusivamente **sequenziale**: non è possibile raggiungere il nodo $i$-esimo in $O(1)$ come in un array. La ricerca binaria richiederebbe $O(n/2)$ passi per raggiungere il centro, e il ragionamento ricorsivo mostra che il costo complessivo resterebbe $O(n)$. L'ordinamento non abbassa il worst-case: l'unica strategia praticabile è la **scansione sequenziale**, che termina appena si trova la chiave $x$ o si supera il suo valore.

**Risultato:** ricerca sequenziale dalla testa della lista.
**Complessità:** $O(n)$ nel caso peggiore.
**Trappola:** rispondere "ricerca binaria $O(\log n)$"; l'accesso al nodo centrale di una lista costa $O(n)$, annullando ogni vantaggio dell'ordinamento.
### Costruzione di un dizionario per ricerche logaritmiche
Ripasso: [[05 - Strutture Dati Elementari e Dizionari#Array ordinato]], [[06 - Alberi di Ricerca BST e AVL#Alberi AVL]].
> [!question] Traccia tipica — 18/07/2022
> Dato un insieme di $n$ chiavi, costruire un dizionario che supporti ricerche in tempo $O(\log n)$. Indicare le strutture dati adatte e analizzare la complessità di costruzione.

**Svolgimento.** Il corso non ha hash table (la nota 05 tratta solo implementazioni elementari). Le uniche realizzazioni con `search` in $O(\log n)$ sono due.

**(a) Array ordinato.** Si ordinano le $n$ chiavi con MergeSort o HeapSort: $O(n \log n)$. Ogni ricerca successiva usa la ricerca binaria: $O(\log n)$ grazie all'accesso diretto agli indici.

**(b) AVL.** Si inseriscono le $n$ chiavi una alla volta in un AVL inizialmente vuoto. Ogni inserzione in un albero di $k$ nodi costa $O(\log k)$; il totale è $\sum_{k=1}^{n} O(\log k) = O(\log(n!)) = O(n \log n)$. Ogni ricerca sfrutta la proprietà BST dell'AVL: $O(\log n)$.

In entrambi i casi la costruzione è $O(n \log n)$ — coincide col lower bound $\Omega(n \log n)$ dell'ordinamento per confronto, quindi è ottima.

**Risultato:** array ordinato (MergeSort/HeapSort + ricerca binaria) oppure AVL ($n$ inserzioni).
**Complessità:** costruzione $O(n \log n)$; ricerca $O(\log n)$.
**Trappola:** proporre una hash table (fuori programma); confondere "ricerca logaritmica" con $O(1)$; usare una lista ordinata (manca l'accesso diretto, la ricerca binaria è inapplicabile: `search` resta $O(n)$).
### Costruzione di un heap binario (Heapify)
Ripasso: [[07 - Code con Priorità e Heap#Heapify — costruzione in O(n)]].
> [!question] Traccia tipica — 22/06/2022, 28/09/2022, 27/09/2023, 16/02/2026, 02/02/2026, 18/02/2025
> Date $n$ chiavi in input non ordinate, costruire un heap binario nel modo più efficiente possibile.

**Svolgimento.** Si costruisce l'heap con la procedura `Heapify`: si chiama `muoviBasso` su ogni nodo interno a partire dall'ultimo, $\lfloor n/2 \rfloor$, risalendo fino alla radice. Il costo totale è proporzionale alla somma delle altezze dei nodi:
$$\sum_{h=0}^{\lfloor \log n \rfloor} \left\lfloor \frac{n}{2^{h+1}} \right\rfloor \cdot h \le n \sum_{h=0}^{\infty} \frac{h}{2^h} = 2n = O(n)$$
La serie $\sum_{h=0}^{\infty} h/2^h$ converge a $2$, quindi `Heapify` è $\Theta(n)$. La nota ricava la stessa complessità col caso 1 del Teorema Master: vedi [[07 - Code con Priorità e Heap#Heapify — costruzione in O(n)]].

Inserire le $n$ chiavi una alla volta con le normali inserzioni costerebbe $O(n \log n)$ — ogni inserzione $O(\log n)$ — che è asintoticamente peggiore.

**Risultato:** `Heapify` applicato all'array non ordinato.
**Complessità:** $\Theta(n)$.
**Trappola:** rispondere $O(n \log n)$, che è il costo di $n$ inserzioni singole, non di Heapify.
### Costruzione heap binomiale
Ripasso: [[07 - Code con Priorità e Heap]].
> [!question] Traccia tipica — 19/02/2024, 13/06/2024
> Costruire un heap binomiale inserendo $n$ chiavi una alla volta. Qual è la complessità totale?

**Svolgimento.** Ogni inserzione in un heap binomiale esegue un **merge** tra il nuovo albero $B_0$ e la foresta esistente — analogo all'incremento di un contatore binario (carry propagation). L'analisi ammortizzata con funzione potenziale $\Phi =$ numero di alberi nella foresta mostra che il costo ammortizzato di ogni inserzione è $O(1)$: il numero totale di link su $n$ inserzioni è $O(n)$, come il numero totale di carry su $n$ incrementi binari.

Il motivo è diverso da Heapify binario (che usa la somma delle altezze): qui si usa l'**analisi ammortizzata**.

**Risultato:** $n$ inserzioni singole; totale $O(n)$ per ammortizzazione.
**Complessità:** $O(n)$ totale.
**Trappola:** rispondere $O(n \log n)$ senza applicare l'analisi ammortizzata.
### Merge di heap binomiali
Ripasso: [[07 - Code con Priorità e Heap]].
> [!question] Traccia tipica — 27/09/2023, 18/07/2025
> Dati due heap binomiali con $n$ e $n^2$ nodi rispettivamente, calcolare la complessità del merge.

**Svolgimento.** Il merge di due heap binomiali con $n_1$ e $n_2$ nodi opera come la somma di due numeri binari di $\lfloor \log n_1 \rfloor + 1$ e $\lfloor \log n_2 \rfloor + 1$ bit. Il costo è $O(\log(n_1 + n_2))$.

Nel caso $n_1 = n$ e $n_2 = n^2$:
$$O(\log(n + n^2)) = O(\log n^2) = O(2 \log n) = O(\log n)$$

**Risultato:** merge in $O(\log n)$.
**Complessità:** $O(\log N)$ con $N = n_1 + n_2$.
**Trappola:** $\log n^2 = 2 \log n \ne \log^2 n$; il merge di heap *binari* non ha un'operazione nativa efficiente analoga.
### Merge di heap binari
Ripasso: [[07 - Code con Priorità e Heap]].
> [!question] Traccia tipica — 25/07/2023, 09/09/2025
> Dati un heap binario con $n^2$ nodi e uno con $n$ nodi, calcolare il modo più efficiente per fonderli.

**Svolgimento.** L'heap binario non supporta un'operazione di merge nativa efficiente. Le due strategie sono:

Strategia A — **Heapify sull'unione**: concatenare i due array ($n^2 + n$ elementi) e applicare Heapify sul totale → $O(n^2 + n) = O(n^2)$.

Strategia B — **inserire il più piccolo nel più grande**: inserire gli $n$ elementi dell'heap piccolo nell'heap da $n^2$; ogni inserzione costa $O(\log n^2) = O(2 \log n) = O(\log n)$; totale $O(n \log n)$.

Confronto: $O(n \log n) \ll O(n^2)$ per $n$ grande, quindi la Strategia B è migliore.

Per due heap di taglia $n$ (simmetrica): Heapify sull'unione $2n$ → $O(n)$, migliore di $O(n \log n)$ inserzioni (es. 09/09/2025).

**Risultato:** inserire il più piccolo nel più grande → $O(n \log n)$.
**Complessità:** $O(n \log n)$ nel caso $n$ e $n^2$; $O(n)$ con Heapify per due heap di uguale taglia $n$.
**Trappola:** non è $O(\log n)$ come per i binomiali; confrontare sempre le due strategie.
### Selezione dei k massimi/minimi
Ripasso: [[07 - Code con Priorità e Heap]].
> [!question] Traccia tipica — 30/01/2023, 26/06/2025, 24/09/2024
> Dati $n$ elementi, trovare i $k$ più grandi (o i $k$ più piccoli). Analizzare la complessità al variare di $k$.

**Svolgimento.** Strategia A — **Heapify + $k$ estrazioni**:
- Heapify sull'intero array: $\Theta(n)$.
- $k$ estrazioni dal max-heap (o min-heap): $O(k \log n)$.
- Totale: $O(n + k \log n)$.

Strategia B — **min-heap di taglia $k$ in scansione** (per i $k$ massimi):
- Si mantiene un min-heap dei $k$ candidati maggiori. Per ogni nuovo elemento, se supera il minimo dell'heap si effettua la sostituzione: $O(\log k)$ per elemento.
- Totale: $O(n \log k)$.

Se $k$ è costante, entrambe le strategie diventano $O(n)$.

Esempi:
- I $5$ più grandi ($k=5$ costante): min-heap di taglia $5$ → $O(n)$ (es. 30/01/2023).
- I $\lceil \sqrt{n} \rceil$ più piccoli: Heapify + $\sqrt{n}$ extractMin → $O(n + \sqrt{n} \log n) = O(n)$ poiché $\sqrt{n} \log n = o(n)$ (es. 26/06/2025).

**Risultato:** Heapify + $k$ estrazioni oppure min-heap di taglia $k$ in scansione.
**Complessità:** $O(n + k \log n)$ oppure $O(n \log k)$; $O(n)$ per $k$ costante.
**Trappola:** per i $k$ massimi serve un *min*-heap di taglia $k$ (non un max-heap), per scartare il minore dei candidati correnti.
### Secondo massimo (o secondo minimo) in vettore non ordinato
Ripasso: [[04 - Algoritmi di Ordinamento]].
> [!question] Traccia tipica — 02/02/2026
> Dato un vettore di $n$ numeri non ordinato, trovare il secondo massimo (o il secondo minimo) nel modo più efficiente possibile.

**Svolgimento.** Basta una singola scansione lineare mantenendo due variabili: il massimo corrente $m_1$ e il secondo massimo corrente $m_2$. Per ogni elemento $A[i]$: se $A[i] > m_1$ si aggiorna $m_2 \gets m_1$ e poi $m_1 \gets A[i]$; altrimenti se $A[i] > m_2$ si aggiorna $m_2 \gets A[i]$. Ogni elemento richiede al più due confronti, quindi la scansione esegue $\Theta(n)$ confronti con $O(1)$ variabili ausiliarie.

**Risultato:** scansione lineare con due variabili ($m_1$, $m_2$).
**Complessità:** $\Theta(n)$ tempo, $O(1)$ spazio.
**Trappola:** ordinare l'array ($O(n \log n)$) o usare un heap è sovradimensionato; bastano due variabili in $\Theta(n)$. Distinto dal secondo minimo in AVL ([[#Selezione e navigazione locale in BST/AVL]], $O(\log n)$), che presuppone la struttura già ordinata.
### Costruzione AVL da sequenza di chiavi
Ripasso: [[06 - Alberi di Ricerca BST e AVL]].
> [!question] Traccia tipica — 25/07/2023, 30/01/2024, 26/06/2025
> Inserire $n$ chiavi una alla volta in un AVL, a partire da albero vuoto. Qual è la complessità totale?

**Svolgimento.** Ogni inserzione in un AVL di $k$ nodi richiede:
- $O(\log k)$ per la ricerca della posizione foglia corretta.
- $O(1)$ rotazioni per il ribilanciamento.

Il costo totale per $n$ inserzioni è:
$$\sum_{k=1}^{n} O(\log k) = O\!\left(\log(n!)\right) = O(n \log n)$$

Non esiste un analogo lineare di Heapify per gli AVL: la proprietà di ricerca impone che ogni chiave venga posizionata correttamente nell'albero, rendendo ogni inserzione intrinsecamente $O(\log k)$.

**Risultato:** $n$ inserzioni sequenziali nell'AVL.
**Complessità:** $O(n \log n)$.
**Trappola:** rispondere $O(n)$ confondendo con Heapify per heap binario.
### Visita BST in-order
Ripasso: [[06 - Alberi di Ricerca BST e AVL]].
> [!question] Traccia tipica — 14/09/2022, 09/09/2024 (decrescente); 30/01/2024 (crescente)
> Dato un BST di $n$ nodi, estrarre tutte le chiavi in ordine decrescente nel modo più efficiente possibile.

**Svolgimento.** La visita **in-order** standard (sottoalbero sinistro → radice → sottoalbero destro) produce le chiavi in ordine crescente. Per l'ordine **decrescente** si esegue la stessa visita in-order invertendo l'ordine dei due sottoalberi: sottoalbero destro → radice → sottoalbero sinistro. La modifica è $O(1)$ nell'implementazione e non richiede spazio aggiuntivo rispetto alla visita standard. Invertire l'output a posteriori richiederebbe invece $O(n)$ spazio supplementare.

Entrambe le visite toccano tutti gli $n$ nodi esattamente una volta.

**Risultato:** visita in-order per l'ordine crescente; in-order con i due sottoalberi invertiti (destro → radice → sinistro) per l'ordine decrescente.
**Complessità:** $\Theta(n)$.
**Trappola:** invertire sx/dx durante la visita ricorsiva (corretto), non accumulare l'output in un array e rovesciarlo a posteriori.
### Merge di due AVL con dimensioni asimmetriche
Ripasso: [[06 - Alberi di Ricerca BST e AVL]].
> [!question] Traccia tipica — 12/09/2023
> Dati un AVL con $n$ nodi e un AVL con $\log n$ nodi (tutte le chiavi del piccolo sono maggiori di quelle del grande), fonderli nel modo più efficiente possibile.

**Svolgimento.** Ricostruire da zero un AVL con tutte le $n + \log n$ chiavi costerebbe $O(n \log n)$ — troppo. La strategia ottima è:
1. Visita **in-order** dell'AVL piccolo per estrarne le $\log n$ chiavi ordinate: $O(\log n)$ (proporzionale alla taglia dell'albero piccolo).
2. **Inserimento** delle $\log n$ chiavi nell'AVL grande: ogni inserzione $O(\log(n + \log n)) = O(\log n)$; totale $O(\log n \cdot \log n) = O(\log^2 n)$.

Costo totale: $O(\log n) + O(\log^2 n) = O(\log^2 n)$.

**Risultato:** in-order del piccolo + $\log n$ inserzioni nel grande.
**Complessità:** $O(\log^2 n)$.
**Trappola:** ricostruire l'AVL unito da zero costerebbe $O(n \log n)$, molto peggiore.
### Forte connessione e componenti fortemente connesse (CFC)
Ripasso: [[09 - Applicazioni della DFS#Componenti fortemente connesse]].
> [!question] Traccia tipica — 14/09/2022, 30/01/2023, 25/07/2023, 13/06/2024, 09/09/2025, 18/07/2025, 02/02/2026
> Determinare se un grafo diretto $G$ è fortemente connesso; se esistono due nodi $s, t$ senza alcun cammino $s \to t$; oppure se esistono $s, t$ tali che $s$ raggiunge $t$ ma non viceversa.

**Algoritmo.** Si richiama l'algoritmo per le **Componenti Fortemente Connesse** come scatola nera — come si fa con Dijkstra o BFS: in $\Theta(n+m)$ restituisce la partizione dei nodi in CFC. Ogni variante del quesito è poi un semplice controllo $O(n+m)$ sul risultato. *(Internamente sono due DFS — una su $G^R$ per i tempi di fine, una su $G$ in ordine decrescente di fine; il prof. non le dà un nome proprio. Il dettaglio sta in [[09 - Applicazioni della DFS#Componenti fortemente connesse]] e qui non va riscritto.)*

**Tre varianti (stesso algoritmo):**
- **(V1)** "esistono $s, t$ senza cammino $s \to t$" / "non tutti mutuamente raggiungibili" $\Leftrightarrow$ **$\ge 2$ CFC** — es. 25/07/2023, 13/06/2024, 18/07/2025.
- **(V2)** "tutti i nodi mutuamente raggiungibili" / "$G$ fortemente connesso" $\Leftrightarrow$ **1 sola CFC** — es. 14/09/2022, 09/09/2025. *Scorciatoia con pivot* (30/01/2023): se basta sapere che un dato $s$ raggiunge ed è raggiunto da tutti, bastano **2 visite da $s$** — una su $G$ e una su $G^R$ — entrambe devono coprire gli $n$ nodi (non serve calcolare tutte le CFC).
- **(V3)** "esiste $s \to t$ ma non $t \to s$" $\Leftrightarrow$ esiste un **arco tra due CFC distinte** nel DAG delle componenti — es. 02/02/2026. È più forte di "$\ge 2$ CFC": se le componenti sono isolate non esiste né $s \to t$ né $t \to s$. Si verifica l'esistenza di un arco $(u,v)$ con $\text{cfc}(u) \ne \text{cfc}(v)$.

**Complessità:** $\Theta(n+m)$ con liste di adiacenza (dominano le 2 DFS; il controllo della variante è $O(n+m)$).
**Trappola:** una *singola* visita da un nodo dice solo chi è raggiungibile *da* quel nodo, non la forte connessione (per il pivot di V2 servono **2** visite, su $G$ e su $G^R$). Per **V3**: "$\ge 2$ CFC" non basta — serve un arco tra CFC distinte (occhio alle componenti isolate).
### Ordinamento topologico e verifica DAG
Ripasso: [[09 - Applicazioni della DFS]].
> [!question] Traccia tipica — 09/09/2025
> Dato un grafo diretto $G$, disporre i nodi su una linea orizzontale in modo che tutti gli archi vadano da sinistra a destra.

**Svolgimento.** La disposizione richiesta è un **ordinamento topologico**. Esso esiste se e solo se $G$ è un **DAG** (grafo aciclico diretto): la presenza di un ciclo renderebbe impossibile la disposizione (almeno un arco andrebbe da destra a sinistra).

Due algoritmi equivalenti:
- **DFS con tempi di fine**: inserire i nodi in ordine decrescente di tempo di fine $f[v]$ → $\Theta(V+E)$.
- **Algoritmo di Kahn**: rimuovere iterativamente i nodi con in-degree $0$; se rimangono nodi al termine è presente un ciclo → non è DAG → $\Theta(V+E)$.

**Risultato:** ordinamento topologico (DFS o Kahn); esiste se e solo se $G$ è un DAG.
**Complessità:** $\Theta(V+E)$.
**Trappola:** tentare l'ordinamento senza prima verificare l'assenza di cicli; con un ciclo l'algoritmo non produce un ordinamento valido.
### Dijkstra da sorgente singola
Ripasso: [[10 - Cammini Minimi e Dijkstra]].
> [!question] Traccia tipica — 04/07/2023, 12/09/2023, 24/09/2024, 30/01/2023, 16/07/2024, 21/01/2025
> Dato un grafo pesato con pesi non negativi, calcolare le distanze minime da $s$ a tutti gli altri nodi e trovare il nodo a distanza massima.

**Svolgimento.** Dijkstra con heap binario esplora i nodi in ordine non decrescente di distanza da $s$. Al termine l'array $d[\cdot]$ contiene tutte le distanze minime. Per trovare il nodo a distanza massima si calcola $\arg\max_v d[v]$ in $O(n)$ a visita conclusa.

Su grafo denso ($m = \Theta(n^2)$) l'implementazione con **array lineare** (senza heap) costa $O(n^2)$ per visita, migliore rispetto all'$O(n^2 \log n)$ dell'heap su grafo completo.

Esempi:
- Nodo a distanza massima da $v$ → Dijkstra da $v$ + argmax → $O(m\log n)$ (es. 04/07/2023).
- Grafo completo, SPT da $s$ → Dijkstra con array → $O(n^2)$ (es. 12/09/2023).
- Nodo più lontano *da* $t$ su grafo **orientato** pesato → Dijkstra da $t$ su $G$ + argmax → $O(m\log n)$ (es. 24/09/2024).
- Distanza $s \to t$ **e** da $t$ a tutti gli altri (grafo orientato) → due Dijkstra indipendenti: una da $s$ (dà $d(s,t)$), una da $t$ (dà l'intero SPT da $t$); non serve il trasposto perché si vogliono le distanze *da* $t$ → $O(m\log n)$ ciascuna (es. 30/01/2023).
- $v$ a distanza $\le L$ da *tutti* gli altri (grafo **non orientato** pesato) → Dijkstra da $v$, poi verifica $\max_u d[u] \le L$ in $O(n)$ → $O(m\log n)$; su grafo non orientato non serve il trasposto (es. 16/07/2024).

**Risultato:** Dijkstra da $s$; argmax dell'array $d[]$ per il nodo più lontano.
**Complessità:** $O(m\log n)$ con heap binario; $O(n^2)$ con array su grafo denso.
**Trappola:** Dijkstra non è corretto con pesi negativi; su grafo denso l'implementazione con array batte quella con heap. Un *lower bound* sui pesi ("pesi tutti $> 100$", es. 21/01/2025) è un **red herring**: non abilita né la BFS (pesi non unitari) né l'Integer Sort, e non cambia la complessità — Dijkstra resta $O(m\log n)$ per qualunque peso positivo.
### Cammino minimo per nodo intermedio obbligatorio
Ripasso: [[10 - Cammini Minimi e Dijkstra]].
> [!question] Traccia tipica — 19/02/2024
> Dato un grafo pesato non orientato, stabilire se esiste un cammino minimo da $s$ a $t$ che passa per il nodo $u$.

**Svolgimento.** Un cammino $s \to u \to t$ che passa per $u$ ha lunghezza $d(s,u) + d(u,t)$. La condizione affinché tale cammino sia anche minimo è:
$$d(s,u) + d(u,t) = d(s,t)$$
Per calcolare i valori necessari si eseguono **due Dijkstra**:
- Da $s$: ottiene $d(s, \cdot)$, in particolare $d(s,u)$ e $d(s,t)$.
- Da $u$: ottiene $d(u, \cdot)$, in particolare $d(u,t)$.

Su grafo **non orientato** vale $d(u,t) = d(t,u)$, quindi non è necessaria una terza Dijkstra da $t$.

**Risultato:** due Dijkstra (da $s$ e da $u$); verifica $d(s,u) + d(u,t) = d(s,t)$.
**Complessità:** $O(m\log n)$.
**Trappola:** su grafo orientato $d(u,t) \ne d(t,u)$ e servirebbe una terza Dijkstra; su grafo non orientato la simmetria la rende superflua.
### Diametro di un grafo non pesato
Ripasso: [[08 - Grafi e Visite]].
> [!question] Traccia tipica — 26/06/2025, 16/02/2026
> Dato un grafo non orientato non pesato con $n$ nodi e $m$ archi, calcolare il diametro (massima distanza in archi tra due nodi qualsiasi).

**Svolgimento.** Il diametro è $\max_{u,v} d(u,v)$. Una singola BFS restituisce solo le distanze da una sorgente fissata — insufficiente per il diametro. L'approccio corretto è eseguire **$n$ BFS**, una per ogni sorgente $u \in V$, e tenere il massimo delle distanze trovate:
$$\text{diametro} = \max_{u \in V} \max_{v \in V} d_{\text{BFS}(u)}[v]$$
Il massimo si aggiorna durante/dopo ogni BFS ($O(n)$ per BFS), costo assorbito dalla BFS stessa.

Per grafo pesato con pesi non negativi si sostituisce ogni BFS con Dijkstra.

**Risultato:** $n$ BFS (una per nodo sorgente); massimo delle distanze.
**Complessità:** $O(n(n+m))$.
**Trappola:** una sola BFS fornisce le distanze da un unico nodo, non il diametro globale; il trucco delle "2 BFS" vale per gli alberi, non per un grafo generale.
### Distanze da più sorgenti — grafo non orientato non pesato
Ripasso: [[08 - Grafi e Visite#Visita in ampiezza — BFS]].
> [!question] Traccia tipica — 22/06/2022
> Dato un grafo non orientato e non pesato $G = (V, E)$ con $n$ nodi e $m$ archi, e due sorgenti $s_1, s_2$ (o un numero costante $k$ di sorgenti), calcolare per ogni nodo $v$ la distanza minima in numero di archi da ciascuna sorgente.

**Svolgimento.** Per ogni sorgente $s_i$ si esegue una BFS indipendente su $G$: ciascuna restituisce le distanze $d_{s_i}[v]$ per tutti i nodi in $O(n+m)$. Con $k$ costante il totale è $k \cdot O(n+m) = O(n+m)$.

Su grafo **non orientato** vale $d(s,v) = d(v,s)$: le distanze *da* $s$ coincidono con quelle *verso* $s$, quindi non occorre il grafo trasposto. La tecnica del trasposto (sezione [[#Distanze/raggiungibilità inverse su grafo trasposto]]) serve sui grafi **orientati**, quando si vogliono le distanze *verso* una destinazione fissa da tutti i nodi — situazione opposta a questa.

**Risultato:** $k$ esecuzioni di BFS, una per sorgente ($k$ costante).
**Complessità:** $O(n+m)$.
**Trappola:** invocare il grafo trasposto è superfluo su grafo non orientato; il trasposto serve per le distanze *verso* un nodo fisso su grafo orientato, non *da* sorgenti note.
### All-pairs shortest paths
Ripasso: [[10 - Cammini Minimi e Dijkstra]].
> [!question] Traccia tipica — 20/02/2023
> Dato un grafo pesato non orientato con pesi non negativi, calcolare le distanze minime tra tutte le coppie di nodi.

**Svolgimento.** Si eseguono **$n$ esecuzioni di Dijkstra**, una per ogni sorgente $s \in V$. Ogni esecuzione con heap binario costa $O(m\log n)$; il totale è $O(nm\log n)$. Con heap di Fibonacci ogni esecuzione costa $O(m + n\log n)$, per un totale di $O(nm + n^2\log n)$.

Su grafo denso ($m = \Theta(n^2)$): Dijkstra con array lineare costa $O(n^2)$ per esecuzione → totale $O(n^3)$.

Floyd-Warshall ($O(n^3)$) è fuori dal programma del Modulo I.

**Risultato:** $n$ esecuzioni di Dijkstra.
**Complessità:** $O(nm\log n)$ con heap binario; $O(n^3)$ con array su grafo denso.
**Trappola:** Floyd-Warshall è fuori programma nel Modulo I; su grafo denso preferire l'implementazione con array.
### Calcolo dell'n-esimo Fibonacci
Ripasso: [[01 - Il Problema di Fibonacci]].
> [!question] Traccia tipica — 13/06/2024, 16/07/2024, 09/09/2025
> Calcolare $F(n)$ (n-esimo numero di Fibonacci) in modo efficiente, minimizzando tempo e spazio.

**Svolgimento.** Il corso numera gli algoritmi (`fibonacci1`–`fibonacci6`). La ricorsione diretta `fibonacci2` ha $T(n) = \Theta(\phi^n)$ ($\phi \approx 1{,}618$) — esponenziale, inaccettabile. Le due scelte ottime stanno ai due estremi del compromesso tempo/spazio:
- **`fibonacci4`** — iterativo con due variabili (si tengono solo $F(i-1)$ e $F(i-2)$): $O(n)$ tempo, **$O(1)$ spazio**. È il minimo spazio. (`fibonacci3` con array è $O(n)$/$O(n)$; `fibonacci5`, potenza di matrice iterativa, eguaglia `fibonacci4` ma è più complesso.)
- **`fibonacci6`** — elevamento al quadrato veloce di $M^{n-1}$ con $M = \begin{pmatrix}1&1\\1&0\end{pmatrix}$ (vale $M^{n} = \begin{pmatrix}F(n+1)&F(n)\\F(n)&F(n-1)\end{pmatrix}$): $O(\log n)$ tempo, **$O(\log n)$ spazio**. È il minimo tempo.

Nel corso **non** esiste un algoritmo con $O(\log n)$ tempo *e* $O(1)$ spazio: `fibonacci6` paga $O(\log n)$ di spazio per lo stack ricorsivo di `potenzaDiMatrice`.

**Risultato:** `fibonacci4` per spazio minimo ($O(n)$ tempo, $O(1)$ spazio); `fibonacci6` per tempo minimo ($O(\log n)$ tempo e spazio).
**Complessità:** $O(n)$/$O(1)$ con `fibonacci4`; $O(\log n)$/$O(\log n)$ con `fibonacci6`.
**Trappola:** la ricorsione diretta `fibonacci2` è $\Theta(\phi^n)$, esponenziale; e `fibonacci6` **non** ha spazio $O(1)$ (la ricorsione costa $O(\log n)$ di stack).

### Distanze/raggiungibilità inverse su grafo trasposto
Ripasso: [[08 - Grafi e Visite]], [[10 - Cammini Minimi e Dijkstra]].
> [!question] Traccia tipica
> Dato un grafo diretto pesato $G = (V, E)$ e un nodo destinazione $t$, calcolare per ogni nodo $v \in V$ la distanza minima del cammino $v \to t$.

**Svolgimento.** Eseguire Dijkstra da ogni nodo verso $t$ costerebbe $O(n \cdot m\log n)$. La soluzione ottima sfrutta il **grafo trasposto** $G^T$: si invertono tutti gli archi. Vale $d_G(v \to t) = d_{G^T}(t \to v)$, quindi basta una sola esecuzione di Dijkstra (o BFS se non pesato) da $t$ su $G^T$ per ottenere tutte le distanze verso $t$ in $G$.

Varianti (ognuna è un quesito reale):
- Distanze verso $t$ in grafo pesato → Dijkstra su $G^T$ da $t$ → $O(m\log n)$ (es. 18/07/2022; somma delle distanze verso $t$: 18/07/2025).
- Distanze verso $t_1$ e $t_2$ in grafo non pesato → 2 BFS su $G^T$ → $O(n+m)$ (es. 28/09/2022, 18/02/2025); la stessa tecnica risponde anche a "tutti i nodi raggiungono $t_1$ e $t_2$?" (2 BFS/DFS su $G^T$ da $t_1$ e $t_2$, sì se entrambe coprono gli $n$ nodi — es. 19/02/2024).
- Esiste un nodo $t$ con distanza verso $s$ maggiore di $L$ → Dijkstra su $G^T$ da $s$, poi cerca $d[t] > L$ → $O(m\log n)$ (es. 02/02/2026, 16/02/2026).
- Verificare che tutti i nodi raggiungano $s$ (o un target $t$) → BFS/DFS su $G^T$ da $s$ (o da $t$): se la visita raggiunge tutti i nodi, la risposta è sì (es. 20/02/2023; verso $t$: 12/09/2023).

**Risultato:** costruire $G^T$, poi BFS o Dijkstra da $t$ (o da $s$) su $G^T$.
**Complessità:** $O(m\log n)$ con Dijkstra; $O(n+m)$ con BFS.
**Trappola:** BFS/Dijkstra da $s$ su $G$ restituisce le distanze *da* $s$, non *verso* $s$.
### Cammini minimi con vincoli sul percorso
Ripasso: [[10 - Cammini Minimi e Dijkstra]].
> [!question] Traccia tipica
> Trovare il cammino minimo da $s$ a $t$ in un grafo pesato, con un vincolo aggiuntivo: il cammino non deve passare per il nodo $w$, oppure deve passare per $w$ usando al più $k$ archi, oppure i pesi sono in $\{1,2\}$.

**Svolgimento.** Il vincolo si gestisce modificando il grafo o lo spazio degli stati:

**(a) Nodo/arco proibito.** Rimuovere $w$ e tutti i suoi archi incidenti, poi Dijkstra su $G \setminus \{w\}$ → $O(m\log n)$ (es. 25/07/2023, 21/01/2025). Per archi proibiti $e_1, e_2$: $G \setminus \{e_1, e_2\}$ (es. 09/09/2024). Se il grafo è **non pesato** e si chiede un cammino di **al più $k$ archi** che evita $w$: rimuovere $w$, poi **BFS** (non Dijkstra) da $s$ su $G \setminus \{w\}$ e verificare $d_{\text{BFS}}(s,t) \le k$ → $O(n+m)$ (es. 27/09/2023).

**(b) Nodo obbligatorio $w$ con al più $k$ archi.** Su grafo non pesato: due BFS (da $s$ e da $t$ su $G^T$); la condizione è $d(s,w) + d(w,t) \le k$ (es. 30/01/2024).

**(c) Pesi in $\{1,2\}$.** Si sostituisce ogni arco di peso 2 con due archi di peso 1 inserendo un nodo intermedio; sul grafo così espanso (tutti archi di peso 1) si applica BFS → $O(n+m)$ (es. 16/07/2024).

**Risultato:** dipende dal vincolo: da Dijkstra su grafo ridotto a BFS su grafo di stati.
**Complessità:** $O(m\log n)$ nel caso generale; $O(n+m)$ con BFS o pesi unitari.
**Trappola:** rimuovendo un nodo occorre togliere *tutti* gli archi incidenti (entranti e uscenti).
### Raggiungibilità su grafo (BFS/DFS con filtri)
Ripasso: [[08 - Grafi e Visite]].
> [!question] Traccia tipica
> Dato un grafo $G$ e un nodo sorgente $s$, determinare i nodi raggiungibili da $s$ considerando solo gli archi con peso $\le x$ (o di un certo tipo/colore).

**Svolgimento.** Si considera il **sottografo filtrato** $G' = (V, \{(u,v) \in E \mid w(u,v) \le x\})$ e si esegue BFS o DFS da $s$ su $G'$. Il costo dipende dalla rappresentazione:
- **Lista di adiacenza**: scorrere ogni lista dei vicini → $O(n+m)$.
- **Matrice di adiacenza**: scorrere ogni riga completa per trovare i vicini → $O(n^2)$ (es. 04/07/2023).

Per **sequenze** di tipi di archi (es. prima un arco rosso poi solo archi blu) si costruisce un **grafo a strati**: lo stato è $(v, \text{tipo\_atteso})$ e si BFS/DFS sullo spazio degli stati allargato (es. 13/06/2024). Diverso è un **filtro statico** (proprietà del singolo arco, non una sequenza): per gli archi "bicolorati" (estremi di colore diverso) si costruisce $G' = (V, \{(u,v) \in E \mid \text{colore}(u) \ne \text{colore}(v)\})$ e si fa BFS/DFS da $s$ su $G'$ → $O(n+m)$ (es. 09/09/2024).

Per "tutti i nodi raggiungono $t$ con al più $h$ archi" → BFS su $G^T$ da $t$ e si verifica $d[v] \le h$ per ogni $v$ → $O(n+m)$ (es. 23/09/2025).

**Risultato:** BFS o DFS sul sottografo filtrato (es. 18/07/2022 per la raggiungibilità verso più nodi).
**Complessità:** $O(n+m)$ con lista di adiacenza; $O(n^2)$ con matrice di adiacenza.
**Trappola:** con matrice di adiacenza il costo è $O(n^2)$, non $O(n+m)$.
### Inserzione batch in heap
Ripasso: [[07 - Code con Priorità e Heap]].
> [!question] Traccia tipica
> Dato un heap binario di $n$ elementi, aggiungere $k$ nuovi elementi nel modo più efficiente possibile. Analizzare per $k = \sqrt{n}$ e per $k = 2$ in heap binomiale.

**Svolgimento.** Due strategie a confronto:

Strategia A — **$k$ inserzioni singole**: costo $O(k \log(n+k))$.
Strategia B — **Heapify sull'unione**: concatenare i $k$ nuovi elementi all'array dell'heap e riapplicare Heapify → $O(n+k)$.

Confronto per $k = \sqrt{n}$ (es. 20/02/2023):
- Inserzioni: $O(\sqrt{n} \log n)$.
- Heapify: $O(n)$.
Poiché $\sqrt{n} \log n = o(n)$ (si verifica dividendo: $n / (\sqrt{n} \log n) = \sqrt{n}/\log n \to \infty$), le inserzioni singole sono asintoticamente migliori. Tuttavia Heapify ha il vantaggio di essere una singola operazione sull'intera struttura e può essere preferito per semplicità implementativa.

Per $k = 2$ in **heap binomiale**: ogni inserzione costa $O(1)$ ammortizzato → $2$ inserzioni → $O(\log n)$ nel caso pessimo (non ammortizzato), $O(1)$ ammortizzato; per $k = 2$ costante il costo è $O(\log n)$ (es. 24/09/2024).

**Risultato:** inserzioni singole $O(\sqrt{n} \log n)$ oppure Heapify $O(n)$; confrontare sempre le due strategie in base a $k$.
**Complessità:** $O(k \log(n+k))$ per inserzioni; $O(n+k)$ per Heapify.
**Trappola:** non confrontare le due strategie e scegliere automaticamente una delle due.
### Selezione e navigazione locale in BST/AVL
Ripasso: [[06 - Alberi di Ricerca BST e AVL]].
> [!question] Traccia tipica
> In un AVL: trovare il secondo minimo; trovare il massimo $< x$ (operazione floor); in una lista ordinata: trovare il $k$-esimo minimo.

**Svolgimento.** In un AVL la navigazione sfrutta la struttura ad albero bilanciato:

**Secondo minimo**: il minimo si trova scendendo sempre a sinistra in $O(\log n)$; il secondo minimo è il suo successore in-order, anch'esso individuabile in $O(\log n)$ (es. 04/07/2023).

**Floor di $x$ (massimo $< x$)**: si scende nell'albero come in una ricerca di $x$, mantenendo un puntatore al migliore candidato trovato finora (ultimo nodo con chiave $< x$ incontrato scendendo a destra). La discesa termina in $O(\log n)$ (es. 24/09/2024).

**$k$-esimo minimo in lista ordinata**: non essendoci accesso diretto, si percorre la lista sequenzialmente per $k$ passi → $O(k)$ (es. 27/09/2023).

**Risultato:** navigazione in AVL $O(\log n)$; percorrenza di lista $O(k)$.
**Complessità:** $O(\log n)$ in AVL; $O(k)$ in lista ordinata.
**Trappola:** visitare tutto l'AVL per trovare il secondo minimo costerebbe $\Theta(n)$; sulla lista non c'è accesso diretto, quindi il $k$-esimo non è $O(\log k)$.
### Ordinamento per confronto generale e subroutine
Ripasso: [[04 - Algoritmi di Ordinamento]].
> [!question] Traccia tipica
> Ordinare $n$ elementi senza vincoli sul dominio. Implementare Partition attorno a un pivot; Merge di due array ordinati.

**Svolgimento.** Senza vincoli sul range il lower bound per l'ordinamento per confronto è $\Omega(n \log n)$ (dimostrazione tramite albero di decisione con $n!$ foglie). Gli algoritmi ottimi sono **MergeSort** e **HeapSort**, entrambi $O(n \log n)$ nel caso peggiore.

**MergeSort**: divide l'array a metà ricorsivamente, poi Merge. La subroutine **Merge** di due array ordinati di taglia totale $n$ percorre entrambi linearmente → $\Theta(n)$ (es. 23/09/2025).

**HeapSort**: Heapify $\Theta(n)$ + $n$ estrazioni $O(\log n)$ = $O(n \log n)$.

**Partition** (Lomuto o Hoare): posiziona il pivot nella sua posizione finale e partiziona gli elementi in $\le$ pivot e $\ge$ pivot → $\Theta(n)$ (es. 23/09/2025).

QuickSort deterministico usa Partition come subroutine: caso medio $O(n \log n)$, ma worst-case $O(n^2)$ (array già ordinato con pivot sul primo elemento).

**Risultato:** MergeSort o HeapSort per ordinamento generale; Merge e Partition come subroutine $\Theta(n)$.
**Complessità:** $O(n \log n)$ per MergeSort/HeapSort; $\Theta(n)$ per Merge e Partition singole.
**Trappola:** QuickSort deterministico ha worst-case $O(n^2)$; non dimenticare il lower bound $\Omega(n \log n)$ per l'ordinamento per confronto.
